## 3a · WHILE YOU BUILD A3 — one rule, and it is not optional

**Money and quantity must never become a JavaScript `number`.**

`src/modules/sales/sale-order/sale-order.service.ts` does exactly that today —
`asNumber()` turns every Decimal into float64, `roundAmount()` is
`Math.round(v*100)/100`, and line 186 is `const AMOUNT_EPSILON = 0.005`. An
epsilon on money is the system telling you its arithmetic drifts;
`Math.round(1.005*100)/100` is `1.00`, not `1.01`, because float64 stores
`1.005` as `1.00499999…`.

The bill does the same work the order does — distribute charges across lines,
roll up, compare against a stored total — so **A3 is where that pattern gets
copied unless it is stopped here.** 79 files in the codebase already use
`Prisma.Decimal` correctly; the order service is the exception.

Five rules, from `sales/SIX_TXN_CONTROLS.md` §6:

1. Keep `Prisma.Decimal` end to end — add, subtract, multiply, divide, compare.
2. **No epsilon comparisons on money.** With decimals, equality is equality.
3. Round **once**, at the column, with a stated mode (`ROUND_HALF_UP`) to the
   column's scale.
4. **Distribute by largest-remainder.** Split a charge across lines and the
   parts must sum to the whole exactly: compute each share, round down, hand the
   remaining paise to the largest remainders. Rounding each line independently
   loses or invents money.
5. The client's totals are a proposal; the server recomputes and they must agree
   to the paise. Add totals to the §10 ignore list.

The database is already safe — **zero** float/real/double columns in `sales`,
`stock`, `accounts` or `inventory`, checked 2026-09-22. This is purely a code
rule.

**`sales/SIX_TXN_CONTROLS.md`** is the full spec behind this: barcode and
scan-to-load on all six, one lifecycle, the GST-cancel-first gate, and the
void + till session work. Read §5a before you write `/bills/cancel` — **an IRN
or a live e-way bill must be cancelled BEFORE the document can be**, and the
screen has to say which one is blocking.

### ⚠️ NEW — a float64 leak writing three stored decimal columns

`stock-voucher.service.ts:3173`:

```ts
private toDecimalNumber(value: string | number | null | undefined): number {
  const parsed = typeof value === 'number' ? value : Number(value);   // ← float64
  return Number.isFinite(parsed) ? parsed : 0;
}
```

and then at 997–1005:

```ts
data.svhTotalQty      = new Prisma.Decimal(this.toDecimalNumber(header.totalQty));
data.svhTotalValue    = new Prisma.Decimal(this.toDecimalNumber(header.totalValue));
data.svhTotalValueWot = new Prisma.Decimal(this.toDecimalNumber(header.totalValueWot));
```

The value round-trips through float64 **before** becoming a Decimal, so the
Decimal faithfully stores whatever float64 already lost. `svh_total_qty` is
`numeric(18,6)` — 18 significant digits, beyond float64's ~15.95.

**`Prisma.Decimal` takes a string directly and keeps it exactly:**

```ts
data.svhTotalValue = new Prisma.Decimal(header.totalValue ?? 0);   // no Number() in between
```

Same pattern is in the generated path's qty rollup —
`round4(lines.reduce((s, l) => s + l.qty + (l.freeQty ?? 0), 0))` sums in
float64 across lines. Sum with Decimal, round once at the end.

This is §3a, still standing, still not optional.
