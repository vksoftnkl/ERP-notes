# Payment voucher + Issued Cheques — backend plan (NestJS)

**For Prathap. Revision 1, 2026-09-14.** The mirror of
`../receipt/plan-backend-receipt.md` rev 3 and `../cheques/plan-backend-
received-cheques.md`; it ASSUMES both §2s have been run and repeats nothing
from them. `payment_flow.md` is the spec; every decision (P1–P15, P11b) is
TAKEN — no open questions, only things you may disagree with. Written
against the schema at 192.168.0.106/ERP (a TEST box: schema authoritative,
rows not) and the conventions the receipt plan set (camelCase payloads,
`i`-prefixed grid params, lowercase dotted settings, the shared voucher
number allocator, `txn_status_log`).

ONE phase. Two menus: **100 Payment** (49 "Bill wise Payment" retired — the
bill-wise panel is always there) and **52 Issued Cheques**. Two screens, one
module.

**The whole module in one line:** money paid to ONE payee (a supplier, a
customer being refunded, or any other ledger), split across instruments,
allocated due-date-first against the bills we owe and the credits we hold,
every non-money line a role-tagged leg (TDS we deduct, discount we receive,
bank charges, interest, round-off), the excess an ADVANCE we spend later; one
voucher for today's money, one per post-dated cheque dated the cheque; our
cheques taking the next leaf of a book and tracked leaf by leaf through their
own register.

### 2.9 `accounts.tds_rates` — a TABLE, not a JSON setting (2026-09-15)

**We deduct TDS when we pay** (user, 2026-09-15), so the rates are master data
with effective dates, not a blob in a setting. The JSON setting proposed in the
first revision is withdrawn.

```sql
CREATE TABLE accounts.tds_rates (
  tdr_id                 uuid PRIMARY KEY DEFAULT uuidv7(),
  tdr_company_id         uuid NULL REFERENCES companys(comp_id),   -- NULL = applies to every company
  tdr_section            varchar(16)  NOT NULL,        -- '194C', '194J', '194Q', '194H', '194I'…
  tdr_section_name       varchar(120) NOT NULL,        -- 'Payment to contractors'
  tdr_deductee_type      varchar(16)  NOT NULL,        -- COMPANY | INDIVIDUAL | HUF | FIRM | AOP | ANY
  tdr_rate               numeric(6,3) NOT NULL,
  tdr_no_pan_rate        numeric(6,3) NOT NULL DEFAULT 20,   -- 206AA
  tdr_threshold_single   numeric(14,2) NOT NULL DEFAULT 0,   -- per payment (194C: 30,000)
  tdr_threshold_annual   numeric(14,2) NOT NULL DEFAULT 0,   -- per FY    (194C: 1,00,000)
  tdr_effective_from     date NOT NULL,
  tdr_effective_to       date NULL,                    -- NULL = open ended
  tdr_is_active          boolean NOT NULL DEFAULT true,
  tdr_remarks            varchar(250),
  tdr_is_deleted         boolean NOT NULL DEFAULT false,
  tdr_created_on timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP, tdr_created_by uuid,
  tdr_modified_on timestamptz, tdr_modified_by uuid,
  CONSTRAINT ck_tdr_rate    CHECK (tdr_rate >= 0 AND tdr_no_pan_rate >= 0),
  CONSTRAINT ck_tdr_dates   CHECK (tdr_effective_to IS NULL OR tdr_effective_to >= tdr_effective_from),
  CONSTRAINT ck_tdr_deductee CHECK (tdr_deductee_type IN
        ('COMPANY','INDIVIDUAL','HUF','FIRM','AOP','ANY'))
);

-- one rate for one section × deductee × day: overlapping periods are refused,
-- the same EXCLUDE discipline as the promotion schemes
ALTER TABLE accounts.tds_rates ADD CONSTRAINT ex_tdr_overlap
  EXCLUDE USING gist (
    coalesce(tdr_company_id, '00000000-0000-0000-0000-000000000000'::uuid) WITH =,
    tdr_section WITH =, tdr_deductee_type WITH =,
    daterange(tdr_effective_from, coalesce(tdr_effective_to, 'infinity'::date), '[]') WITH &&
  ) WHERE (tdr_is_deleted = false AND tdr_is_active = true);
```

**The lookup**, at the payment date: the party ledger's
`led_tds_nature_of_payment` gives the **section**, `led_tds_deductee_type` gives
the **deductee type** (falling back to a row with `ANY`), and the row whose
period contains the payment date gives the rate. `led_pan_no` empty →
`tdr_no_pan_rate` (206AA, 20 %). Company-specific rows win over the
`tdr_company_id IS NULL` defaults.

**The seed returns WHY, not just how much.** `tds-seed.ts` answers with
`tdsRateSource` = `MASTER` | `NO_PAN` | `BELOW_THRESHOLD` (and `CERTIFICATE`
once that layer exists — `../accounts/statutory_masters.md` §0, not built),
which the line carries and `acc_tds_register` stores. It is one `varchar(16)`
and it is what keeps the certificate layer addable later without leaving every
earlier deduction unexplainable. Notes (17).

**Thresholds are checked, not stored.** `tdr_threshold_single` is read against
this payment; `tdr_threshold_annual` against the sum of payments to that party
in the financial year — computed, exactly like the TCS 50-lakh threshold
(`../receipt/plan-backend-receipt.md` §2.14). Below the threshold the client
still shows the line with zero, so the operator can see why.

**Seed rows** (2026-27, `tdr_company_id` NULL): 194C 1 % INDIVIDUAL / 2 %
COMPANY, single 30,000, annual 1,00,000 · 194J 10 % ANY, 30,000 · 194H 5 % ANY,
15,000 · 194I 10 % ANY, 2,40,000 · 194Q 0.1 % ANY, 50,00,000. Verify against
the current Finance Act before loading — these are the shape, not the authority.

**A master screen is owed eventually** (grid + entry, the `tax_rate_master`
shape), but the table and the seed are enough for Payment to work. Not in this
phase.

The register that TDS is reported from is
`../receipt/plan-backend-receipt.md` §2.14 (`acc_tds_register`, 26Q) — written
at post, never re-summed.

## 4. The endpoints

### 4.1 `GET /api/v1/payments/open-items`

Query: `payee_kind` (SUPPLIER | CUSTOMER | LEDGER — it still decides which
bill types and which panels the screen shows), **`party_id`** (the one id —
supplier, customer and ledger are the same value, §2.3), `company_id`,
`on_date`. Nothing is resolved. Returns

```jsonc
{ "bills":   [ { "billId", "billAccYear", "billType", "docRefno", "docDate", "dueDate", "daysToDue",
                 "billAmount", "pendingAmount", "status", "pdcIssued", "discSuggested" } ],  // P6
  "credits": [ { "billId", "billAccYear", "billType", "docRefno", "docDate", "pendingAmount", "srcDocType", "srcDocId" } ],
  "summary": { "totalOwed", "billCount", "overdueCount", "creditsHeld", "pdcIssuedOut" },
  "party":   { "ledId", "ledName", "groupName", "isBillByBill", "isCashOrBank",
               "isTdsApplicable", "tdsDeducteeType", "tdsNature", "tdsSection", "tdsRate", "panPresent",
               "favouringName", "cashDiscPerc", "creditDays",
               "bank": { "name", "account", "ifsc", "upi", "beneficiaryName" } } }   // default acc_ledger_bank_accounts row
```
SUPPLIER: `payment_flow.md` §4.3's two SELECTs. LEDGER: `bills` and
`credits` empty; `party` filled. CUSTOMER: `bills` empty; `credits` = the
customer's CR items with pending > 0 (ADVANCE, SALES_RETURN) — P12.
`isCashOrBank = true` ⇒ the client refuses the payee ("use Contra 104"); the
server refuses at create too. `tdsSection / tdsRate` come from `tds-seed.ts` — the **`accounts.tds_rates`
table** (§2.9) looked up by `led_tds_nature_of_payment` (section) ×
`led_tds_deductee_type` × the payment date, with `led_pan_no` empty ⇒
`tdr_no_pan_rate` (206AA). Also returns `tdsThresholdSingle` /
`tdsThresholdAnnual`, `tdsPaidThisYear` and **`tdsRateSource`**, so the screen
can show why a line is zero — and why the rate is what it is. No paging cap.

### 4.5 `POST /api/v1/payments/post`

```jsonc
{ "avhCompanyId", "avhBranchId", "avhAccYear", "avhVoucherId",   // the four keys — same shape as the receipt's §4.0
  "allocations":    [ { "billId", "billAccYear", "amount": 60000, "discount": 0,   "roundOff": 0 },
                      { "billId", "billAccYear", "amount": 45000, "discount": 0,   "roundOff": 0 },
                      { "billId", "billAccYear", "amount": 19900, "discount": 100, "roundOff": 0 } ],
  "creditsApplied": [ { "billId", "billAccYear", "amount": 5000, "againstBillId", "againstBillAccYear" } ],
  "otherLineBills": [ { "lineNo": 1, "billId", "billAccYear", "amount": 75 }, { "lineNo": 1, "billId", "billAccYear", "amount": 50 } ],
  "writeoffApprovedBy": null,
  "onAccount": 0 }
```
`amount` = the bill's TOTAL settlement by this payment excluding discount /
round-off (money + TDS + credits — the engine splits it). The server
recomputes everything and refuses a mismatch. Returns the numbered headers
(payment + PDC vouchers), the rows written, the ADVANCE bill id, the
register rows with their LEAF numbers, the book's new `chb_next_leaf`, and
the print keys (`advice`, `cheques[]`).

### 4.9 Cheque books — ~~`GET /cheque-books/list`~~ (registered grid instead), `GET /cheque-books/get`, `POST /cheque-books/create` (upsert), `POST /cheque-books/close`

`create`: `{ chbId?, chbCompanyId, chbBankLedgerId, chbBookNo, chbLeafFrom,
chbLeafTo, chbLeafWidth, chbFormat, chbRemarks }` — from/to numeric, width

false; refused while HELD cheques of the book exist? No — a book closes when
the paper is gone; HELD cheques are already out. Allowed.

### 4.10 Issued cheques — ~~`/issued-cheques/list`~~ (registered grid), `/get`, `/history`, `POST /issued-cheques/print`, `/presented`, `/returned`, `/stop`, `/void`, `/replace`

All on `apd_tra_type = 'P'`; a request naming an R row is a 409.

**Key shape:** a register row is addressed the way a voucher is —
`companyId · branchId · accYear · apdId` — so every route below reads the same
as the voucher routes, with `apdId` in place of `voucherId`. (`print` takes an
array of them.) Flag it if any of these genuinely needs a different shape.

- **print** `{ apdIds: [{apdId, apdAccYear}], formatId?, dateOverride?,
  crossed }` — no status change; `apd_printed_on = now()`, `apd_print_count
  + 1`, log 'PRINTED'; returns the `cheque_print` dataset rows (or the print
  pipeline's key). Refused on CANCELLED / REPLACED / BOUNCED rows.
- **presented** `{ apdId, apdAccYear, bankDate, remarks }` — HELD only;
  `bankDate ≥ apd_instrument_date`, in an open year; register → CLEARED,
  `apd_clear_date = bankDate`, `apd_clear_voucher_id` NULL (P11b); UPDATE
  the payment's bank leg `av_recon_date = bankDate` (the leg with
  `av_ledger_id = apd_bank_ledger_id` on `apd_voucher_id`); log. No voucher.
- **returned** `{ apdId, apdAccYear, returnDate, reason, reasonText,
  bankCharge }` — HELD only (a PRESENTED cheque cannot be returned — that is
  a bank error, out of scope). `payment_flow.md` §5.4: the `ChqBnc` voucher
  (CR party / DR bank for the amount; DR `BANK_CHARGES` / CR bank for the
  charge), negative `abj` rows for `abj_cheque_id = this`, the ADVANCE
  reversal + cascade, register → BOUNCED with `apd_bounce_*`,
  `apd_bounce_voucher_id = apd_charge_voucher_id`; log. One transaction.
- **stop** `{ apdId, apdAccYear, reason, remarks }` — HELD only; the
  reversal `Pmt` voucher, negative `abj` rows, ADVANCE undone; register →
  CANCELLED (`ck_apd_cancelled` wants the reason); log.
- **void** `{ chequeBookId, reason }` — consumes `chb_next_leaf` (row lock):
  inserts a register row `apd_tra_type 'P'`, amount 0, `apd_status
  'CANCELLED'`, no tender / voucher / party, `apd_bank_ledger_id` = the
  book's bank, `apd_remarks` = reason; advances the book; log. The spoilt-
  blank case. Also `{ apdId, apdAccYear }` form for "spoilt while printing"
  on a HELD row: = stop (above) + the leaf stays consumed; Replace follows.
- **replace** `{ apdId, apdAccYear, chequeBookId, instrumentDate, amount?,
  allocations?: [...] }` — BOUNCED or CANCELLED-by-stop only. New register
  row HELD with the book's next leaf, `apd_replaced_by_id / _acc_year` on
  the old (→ REPLACED); a NEW `Pmt` voucher DR party / CR bank (dated the
  cheque when post-dated, `avh_against_voucher_id` = the original payment),
  allocations through the engine (auto FIFO over the bills the old cheque
  had settled when the array is empty); `apd_voucher_id` on the new row;
  log on both. One transaction.
- **history** — `txn_status_log` for the leaf, newest first.

## 5. Service logic

### 5.1 Draft save

1. Payee: resolve the ledger by kind (§4.1); live, visible to the company;
   NOT a cash / bank ledger ("use Contra 104"); a customer only when the
   customer holds unapplied CR items (else "nothing to refund").
2. Date in an OPEN, unlocked year.
3. Tender rows: master live for company/branch, `ttm_allow_in_return`;
   `tdAmount > 0`; a BANK row carries `transferMode` and the beneficiary
   snapshot (defaulted from `acc_ledger_bank_accounts` when omitted); a
   CHEQUE row carries `chequeBookId` (an active book of the tender's bank
   with free leaves), `tdInstrumentDate`, `favouring`; `tdIsPdc` computed;
   `tdMdrAmt` from the master unless `tnd_edit_surcharge`.
4. Other lines: role must exist and be mapped; a free ledger live and not
   the payee; `amount ≥ 0`. Seeds the client mirrors: `TDS_PAYABLE` when
   `led_is_tds_applicable` (rate per `tds-seed.ts`; on the on-account part
   too — P5; the operator may override the amount, never remove the line);
   `BANK_CHARGES` from every `tdMdrAmt > 0`; `DISCOUNT_RECEIVED` = Σ bill
   discounts (checked at post). LEDGER payee: no bill-settling lines except
   TDS.
5. `avh_doc_amount = Σ tdAmount`. Header DRAFT, no number,
   `avh_draft_lines` = the other lines. Replace semantics. One transaction.

### 5.2 Post — in this order, in one transaction

1. Load the payment `FOR UPDATE`; **refuse unless DRAFT** — Post is always
   post-from-draft.
2. Re-validate 5.1. Every date (payment + each PDC instrument date) in an
   OPEN, unlocked year.
3. **Lock the open items** named in `allocations[]` / `creditsApplied[]`
   `FOR UPDATE`; per bill `amount + discount + roundOff ≤ pending` NOW; per
   credit `amount ≤ pending` NOW; else 409 naming the item. LEDGER payee:
   both arrays must be empty; CUSTOMER: `allocations[]` empty,
   `creditsApplied[]` non-empty and `onAccount = 0`.
4. **The identity**, to the paisa:
   `Σ tdAmount + Σ CR-other (settling) + Σ creditsApplied = Σ allocations.amount + Σ discount + Σ roundOff(CR) + onAccount + Σ DR-other (additions)`.
   `BANK_CHARGES` excluded on both sides. `BALANCES_WRITTEN_BACK` above
   `accounts.writeoff_approval_above` needs `writeoffApprovedBy`. Refuse on
   any mismatch; the message names the six figures.
5. **Allocation engine** (the receipt's, direction OUT): order credits →
   settling deductions (TDS pinned via `otherLineBills[]` else pro-rata;
   discount per bill as sent) → instant money → cheques current-dated →
   post-dated by date, walking bills in list order; output the `abj` row set
   of `payment_flow.md` §4.4 (`abj_dr_cr 'DR'` on CR bills, the pair for
   each credit), which voucher each row belongs to, and the on-account split
   per voucher.
6. **Leaves:** for each CHEQUE row, `cheque-book.service.takeNextLeaf(bookId)`
   — `SELECT … FOR UPDATE`, refuse when finished ("book 000451–000500 is
   finished — open the next"), write the leaf into `td_ref_no`, advance
   `chb_next_leaf`. Then one `acc_pdc_register` 'P' row per cheque (§4.6 of
   the flow), `apd_posting_mode 'ON_RECEIPT'`.
7. **Numbers:** for the payment and for each PDC
   voucher (dated the cheque) through the shared allocator.
8. **Headers:** the payment; one DRAFT header per post-dated cheque with
   `avh_voucher_date = instrument date`, `avh_against_voucher_id` = the
   payment, `avh_party_id`, `avh_doc_amount` = the cheque.
9. **Legs** (`payment_flow.md` §4.2): per voucher, `av_row_no` 1..n; CR per
   instrument (bank gross of its charge — the `BANK_CHARGES` DR leg is the
   other half); CR / DR per other line with `av_role`; the credit pair's
   holding leg (CR the debit note's ledger / CR `ADVANCE_PAID` ledger,
   `av_role NOTE_ADJUST / ADVANCE_ADJUST`); the on-account leg (DR
   `ADVANCE_PAID`); ONE DR party for the rest. LEDGER payee: DR the ledger
   gross, CR `TDS_PAYABLE`, CR instruments. CUSTOMER: DR the holding ledger
   / CR instruments. Trigger derives the totals.
10. **Adjustments:** the engine's rows; post-dated rows
    `abj_is_post_dated = true`, `abj_adj_date` = the cheque date. Trigger
    2.1 (receipt) moves the caches.
11. **On account:** one ADVANCE (DR) bill per voucher with a remainder
    (`abl_src_doc_type 'PAYMENT'`, `abl_branch_id` = the payment's).
12. **Tender rows:** `td_voucher_id`; BANK rows `td_settle_status =
    'PENDING'` when `tdRefNo` is empty, else `'SETTLED'`.
13. `apd_voucher_id` on each register row = the voucher carrying that
    cheque's legs.
14. **Headers to POSTED, last;** `avh_adjust_amount`, `avh_opposite_ledger_id`,
    `avh_draft_lines = NULL`; `ck_avh_balanced` / `ck_avh_no` fire here.
15. `fn_abl_regularise_pdc(CURRENT_DATE)` for cheques dated today.
16. `txn_status_log` 'POSTED' on the payment and 'ISSUED' on each leaf.

A failure after step 6 rolls the leaf back with the transaction — keep
`takeNextLeaf` inside it, never in a prior call.

## 9. Test checklist

1. Supplier, one bill, NEFT exactly pending → CLOSED, legs DR party / CR
   bank, identity holds, `td_settle_status PENDING` (no UTR).
2. The worked example (§4 of the flow): two vouchers, six + two legs,
   eight `abj` rows, leaf 000451 taken, `chb_next_leaf = 000452`, 0102
   pending unchanged until 20-09, then 0 after `fn_abl_regularise_pdc`.
3. TDS: applicable ledger, no TDS line sent → server seeds it; wrong rate
   sent → 409; PAN missing → 20 %; on-account part taxed too.
4. Discount seeded within `sup_credit_days`, not outside; DISCOUNT rows per
   bill; `DISCOUNT_RECEIVED` leg = Σ.
5. Credit applied: pair rows, holding-ledger leg, both bills' pendings
   move; applied > pending → 409.
6. On account 5,000 → `ADVANCE_PAID` leg + ADVANCE (DR) bill; a purchase
   bill's adjust panel spends it (the receipt's pair mirrored); Cancel then
   refused.
7. Cash / bank payee → refused at open-items AND at create. Customer with
   no credits → refused. Customer refund > credit → refused; = credit →
   credit CLOSED, no TDS, no bills.
8. LEDGER payee with TDS-applicable ledger (rent 194I): DR rent gross, CR
   TDS 10 %, CR bank net; no `abj`.
9. Cheque book: finished book → 409 naming it; two concurrent posts on the
   same book get different leaves; a failed post gives the leaf back
   (rollback); VOID consumes a leaf and creates a CANCELLED row with no
   voucher.
10. Print: counts, logs, refuses a CANCELLED row; re-print increments.
11. Presented: HELD → CLEARED, `av_recon_date` set on the right leg,
    `apd_clear_voucher_id` NULL passes the P11b CHECK; a second Presented →
    409; Presented on an R row → 409.
12. Returned unpaid: ChqBnc legs balance, bills reopen with the right
    pendings, ADVANCE cascade, leaf consumed; then Replace → new leaf, new
    voucher, fresh allocations, old row REPLACED.
13. Stop on HELD → reversal, bills reopen; Stop on PRESENTED → 409.
14. Cancel: reverses payment + PDC vouchers; refused when a cheque is
    PRESENTED, when the NEFT is SETTLED, when the ADVANCE is spent.
15. Post runs straight off a DRAFT; there is no approval gate to test.
16. Header edit whitelist; `ux_avh_doc_refno` duplicate → 409 naming the
    earlier payment.
17. Every date check: PDC dated into a locked year → 409.
18. `ck_avh_balanced` cannot be tricked: totals are derived (receipt §2.4).
