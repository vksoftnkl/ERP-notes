## 2. What the sale bill posting actually does today — the defect list

`bill-posting.helper.ts` (`postBillToAccounts`), verified against the live rows:

1. **No `acc_vouchers` legs.** It writes one `acc_voucher_header` and one `acc_bill_balance` DR
   row. The helper says so in its own comment: *"the per-ledger split lives in acc_vouchers, which
   this helper does not write."* Live: 21 type-3 headers, **0 legs**. Since
   `tr_av_refresh_totals` (installed 2026-09-17) only fires on `acc_vouchers`, the bill's stamped
   `avh_total_debit/credit` (137,752 / 137,752 on `bil00030`) are never corrected, so
   `ck_avh_balanced` passes on a voucher that has no legs at all. The day book, trial balance and
   every Sales / Output-tax ledger are empty of every bill ever raised.
2. **No stock movement.** `stock.stock_voucher` holds OPENING / PHYSICAL / TRANSFER_OUT only;
   `stock_ledger` has no `SALE` row. `sbi_stock_id` / `sbi_batch_no` are 0 of 56 live lines, though
   the README calls them required.
3. **No doc register row**, so nothing can ever acquire an IRN or an e-way bill
   (`acc_voucher_doc_einvoice` is 1:1 with a register row it does not have).
4. **Status moves through `/create`.** There is no `/post`, `/cancel`, `/amend`; the client sends
   `sbStatus` and the update path re-syncs a POSTED bill in place — every edit of a posted bill is
   silently an amend. `POST /bills/delete` **cancels the sale order behind the bill** and leaves
   the bill untouched (README: *"Despite the path, this deletes nothing"*).
5. **Tenders are saved, adjustments are posted** (`bill-adjustment.helper.ts` — advance / credit
   note set-off, reversal rows, allocation re-settled). This half is right and should be kept;
   its `ALLOCATION` rows for cash tenders are not written (the seeded `abl_alloc_amount` stands
   in), which is the receipt module's `acc_bill_adjustment` convention in reverse.
6. No loyalty accrual, no promotion usage, no TCS figure (`sale_bill` has no `sb_tcs_*`).

The **sale order** is in better shape: `order-advance-posting.helper.ts` writes header **and**
legs (DR tender ledger / CR advance liability, per tender row), the ADVANCE bill, the PDC row, and
cancels/retires on edit or delete. Fulfilment (`soi_delivered_qty` etc.) is re-derived from POSTED
bill lines, over-delivery revises the order up, and `PUT /cancel-lines` closes the balance. This is
the second pattern to copy (alongside the receipt) for "a document that posts money".

## 3. Stock — how sales plugs in

The engine is **in NestJS**, not in the database: `stock-voucher-posting.helper.ts` reimplements
`fn_svh_post` / `fn_sml_apply` (lots, ledger, balance, moving average, negative-stock policy, lot
totals) as seven set-based statements in the caller's transaction, and cancel is the same engine
run over reversal rows. The DB keeps only the guards (`tr_sml_forbid_delete`, `tr_sml_immutable`,
`tr_sml_freeze_guard`). `stock_ledger` deliberately has **no Prisma model**. The transfer routes
still call the share's SQL functions, which are not installed, so despatch fails today
(documented in the helper as "the honest outcome").

What that means for a sale:

- A bill / DC / return does **not** create a `stock_voucher`; it writes `stock_ledger` rows with
  `sml_src_module='SALES'`, `sml_src_doc_type` ∈ {SALE_BILL, DELIVERY_CHALLAN, SALE_RETURN,
  DC_RETURN}, `sml_src_doc_id` = the document. `ux_sml_source` (source, line, split, godown, lot,
  direction) makes posting idempotent. The grain is exactly `sale_bill_item`'s
  (line × split × godown × lot) — the ledger's own comment says posting a bill is
  "a straight INSERT … SELECT".
- The engine's phases 3–7 (`writeLedger` → `applyBalances` → `applyItemCost` →
  `assertNegativeStockPolicy` → `refreshLotTotals`) are keyed on `sml_src_doc_id`, so they can be
  lifted into a shared `StockPostingService.postRows(tx, rows)` that every sales document calls.
  Phases 1–2 (lot resolution from batch/MRP/expiry) are the inward path; an outward names the lot
  it takes from (`sbi_stock_id` → must become `sbi_lot_id`, see §10).
- Outward rows carry **COGS**: `sml_cost_rate/_value` are stamped from the branch average or lot
  cost per `stp_valuation_method`, `sml_doc_rate` is the selling price. So the COGS figure exists
  on every sale row whether or not accounts uses it (§9).
- `stock_balance.sbl_available_qty = on_hand − reserved`; `stock_reservation` is designed for
  the sales order and unused. Nothing today reserves; a confirmed order does not hold stock.
- The negative-stock rule is three switches (company `comp_negstk_apl`, godown
  `gdl_negative_stock`, item `item_allow_neg_stock`) resolved by `/item-price` and the engine's
  `stp_allow_negative` BLOCK/WARN/ALLOW. Two answers to one question — §10.
- `inventory.item_stock_ledger` (legacy, 77 OPENING rows via `stock-reconciliation.processor`) is
  a dead path and must not get a sales writer.

## 4. Accounts — the receipt is the pattern, and what a sale adds

`accountsModule/receipt` (15k lines) is the reference: DRAFT (no number, no legs, no bill rows)
→ `/post` in one transaction of fifteen ordered steps, POSTED set **last** so
`ck_avh_balanced` judges real legs → `/cancel` = numbered reversal voucher + negative adjustment
rows → `/amend` behind `accounts.allow_posted_amend` (unwind in place, revision counter,
optimistic lock) → `/delete` for a DRAFT only. Legs are found by **role** through
`acc_ledger_map` (36 rows seeded, `SALES`, `SALES_RETURN`, `OUTPUT_CGST/SGST/IGST/CESS/ACESS`,
`ROUND_OFF`, `DISCOUNT_ALLOWED`, `ADVANCE_RECEIVED`, `TCS_PAYABLE` all present), with per-rate
overrides in `inventory.tax_rate_ledger` (empty). Bill caches are recomputed by
`BillBalanceRecomputeService` (the TypeScript `fn_abl_recompute`), not a trigger.

What a sale bill has to write that the receipt never does:

- **Multi-leg CR side by rate**: one CR per (SALES ledger) + one CR per output-tax ledger per
  rate, from `sbi_tax_id` (the frozen `tax_rate_master` row) — the 3.0 screen already sums per
  item ledger (`salLgrSums` / `taxLgrSums`) and posts one leg per ledger; ours resolves the ledger
  by role + rate + supply nature server-side (`fn_tax_ledger_for` logic, in TS).
- **Charges**: after-tax `cd_tax_apl` charges post to `cd_ledger_code` with their own GST legs;
  before-tax charges are inside the taxable base (do NOT post separately — the trap recorded in
  `sale_bill_posting_flow.png`). Cash discount / scheme discount / round-off / TCS as in that flow.
- **Tenders → legs**: DR tender ledger per row (surcharge CR), exactly as the order does; a
  `CREDIT` tender posts nothing (the party DR stays open); `ADJUST` never reaches tenders.
- **Party leg**: DR customer for `sb_bill_amt`; a walk-in must post to a party — see Q-14.
- **COGS / inventory legs** — §9.

Roles that do **not** exist yet and will be needed: `COGS`, `INVENTORY` (stock-in-hand), possibly
`GOODS_DELIVERED_NOT_BILLED`. Voucher types missing: DC, DC Return, Sales Return (3.0's credit
note). Also missing: `22_item_income_ledger.sql` (item/group revenue ledger override) is not
deployed; every item credits the one `SALES` ledger today.

### 7a. What the 3.0 database functions settle (read 2026-09-20 from the `3.0` database on .106)

The bodies of `public.fsales` (180 k chars, 59 flags), `fsales_return` (21 flags),
`feinvoice_system` (22 flags), `fsales_dispatch` and `floyalty_schemes` were read. What the
screens send (above) is confirmed, and these are the facts that only the functions held:

- **The bill's accounting legs are built on the client and stored as sent.** `fsales` flag 1
  takes `VoucherJSON` and inserts each `{Lgr, OLgr, CrDr, Amount}` into `acc_vouchers` verbatim;
  the only server-side rule is a balance check (Σ Cr − Σ Dr within ₹0.50, else
  `RAISE 'Account entry blocked due to amount difference'`). The ledgers were hard-coded in
  the screen and named in `acc_ledgers`: Sales A/c 100020, Sales Return 100030, GST Amount
  100092, Cess 100139, TCS on Sales 100150, Packing Charges Received 100009, Freight 100131,
  Loading 100132, Discount On Sales (CD) 100145 / Cash Discount On Sales 100147, Scheme Discount
  100152, Round Off 100012, Cash In Hand 100013, Card Swiping Charges 100151, TDS on Receipt
  100162, Cheques-in-hand 100002. Per-item sales and tax ledgers (`lgr_loc_sal` etc.) were
  summed into one leg per ledger. **Ours reverses this**: the server derives every leg by role.
- **"Postpone account entries"** (`configs` 108): a bill can be saved with `sal_del_status =
  'Pending'` and its legs written later by flag 57 ("update bill delivery status") — i.e. 3.0
  already separated *save* from *post*, by a delivery-status flag. Our DRAFT → POSTED is the
  same idea made explicit.
- **Stock at the bill** is FIFO over `stocks` rows (by godown, stock date), MRP-wise or
  batch-wise per `batch_config`, with `fsplit_stock` auto-breaking a larger unit when short,
  one `sale_details` row per stock row consumed, a `delivery` row (−qty) per row, and a
  verification that Σ sale qty = −Σ delivery qty. Negative stock is *not* blocked server-side on
  the bill (the check is commented out); it is on the DC.
- **Loyalty earn is inside `fsales`**, after the bill is written, for every live scheme that
  matches the customer (area / type / list / all), bill type (cash/credit/all) and date. Four
  scheme kinds: `Item Master PV` (Σ item.loyalty_pv × qty), `Invoice Amount` (slab
  `lspt_exceeds` → `lspt_factor` × amount), `Invoice Item Amount`, `Invoice Item Qty` (per
  brand/group/item). Writes `loyaltysch_tran_dtl` (type 5) + rolls `loyaltysch_tran_hdr`.
  **Redemption** is a tender row of type 6: points = amount ÷ `ls_point_inr`, written as a
  negative `tran_dtl` (type 24). **A return reverses** points for the returned lines (negative
  type-5 rows), and **an edit/delete of the bill deletes and re-earns**. Gift redemption
  (`floyalty_schemes` flag 8) is its own document. All of this maps onto 13's `loyalty_ledger`
  with `lld_txn_type`; the four earn kinds are 12's `lsc_apply_on` × slab.
- **Sales-return redemption in the tender** (type 5): `RRNJSON` names open credit-note
  `acc_pendings` (cr_dr 'Cr', origin_voucher = the return) and writes a DR settlement row per
  credit — the 3.0 form of our `adjustments[]` / NOTE_ADJUST pair.
- **Salesman commission** (`fsalesman_commision`) and **agent loyalty**
  (`app_utils.fx_agent_loyalty_points`) run at every bill save/return — both out of this scope
  (§7 "defer").
- **Return (`fsales_return` flag 1):** voucher type 6, numbered `prefix/Sre/n`; legs come as XML
  from the client and are stored with `status = ireturn_apprvd`, i.e. **approval is the posting
  gate** — `configs` 99 "Sales Returns/Credit Note must be authorized by admin" = Yes, and flag 20
  (approve) flips `acc_vouchers.status` and `acc_pendings.status` to true. Settlement:
  `Return Cash` → a cash tender row (type 1) and no pending; `Adjust Balance` → FIFO over the
  customer's open bills, **the original bill first**, one DR `acc_pendings` row per bill
  (pay_mode 'Sales Return'), remainder → a CR pending (on account); `Save as Advance` → the
  whole amount as a CR pending. `return_type = 'Claim'` skips the stock add-back entirely
  (supplier expiry claim; `expiry_return*` tables). Stock add-back is per original `sale_det_id`
  (`sales_data` array, `sale_qty − return_qty` cap), creating a new `stocks` row when the return
  godown or year differs. `sale_details.return_qty` is the bill-side cache. E-invoice / e-way
  applicability is answered at save from company flags + thresholds + `configs` 73.
- **E-invoice / e-way JSON** (`feinvoice_system` 14 / 16) is built from `sales_tranlog` (the
  GST snapshot row: party / ship-to / dispatch / values / IRN / EWB / cancel columns) +
  `voucher_taxlog` (line-wise HSN, rate, taxable, tax) — exactly the split our
  `acc_voucher_doc_register` + `_doc_detail` make, so the JSON builder ports onto the register
  1:1 (`DocDtls.Typ` = INV | CRN from `supply_type`, `Pos` = customer state, `EwbDtls` only when
  vehicle + EWB are known, e-way `fromGstin` / `toGstin` swap on inward supply, `URP` for
  unregistered). Cancel reasons 1–4, Part-B vehicle update, extension and manual EWB entry are
  register-row updates (flags 17–20).
- **Dispatch (`fsales_dispatch`)** is a *load sheet*: one row per lorry (transporter, vehicle,
  driver, loadmen, weights, freight/cooly per bill) over many bills, stamping `del_taken` and
  the crew onto each bill and generating one e-way bill per dispatch. That is what "Dispatch
  Pendings" / "Bill Delivery Update" (menu 226) were. Deferred (§7), but it is the natural home
  for e-way-per-vehicle later, not the bill.
- **Delete** in 3.0 is a status flip plus `deleted_transactions` row, with stock and pendings
  reverted and loyalty un-earned — a soft cancel, no reversal rows. Ours reverses (§4).

## 8. Tally and GoFrugal — the behaviours worth adopting

Stated from product knowledge, as behaviours to copy or reject, not as rules of ours.

- **Delivery Note before invoice (Tally):** the DN moves stock, the invoice "against" the DN
  moves accounts only, one invoice can absorb several DNs and one DN can be invoiced in parts;
  tracking numbers link the two; a DN not yet invoiced shows in "Sales Bills Pending". Rejections
  In is the DC-return equivalent. **Adopt** all of it (it is the user's flow list).
- **Credit note "against reference" (Tally):** the return names the original invoice, which is
  what GSTR-1 CDNR needs (original invoice no + date) — our register has `gdr_doc_note_no/date`
  and `gdr_orig_doc_no/date` for exactly this. **Adopt**: a return against a bill is the norm; a
  free return is allowed but flagged (Q-2).
- **Tally is periodic** (no COGS entry; closing stock valued at period end); **GoFrugal is
  perpetual** in effect (stock value moves per bill and gross margin reports are per bill). §9.
- **GoFrugal:** returns land in a chosen bin (saleable / damaged); loyalty points accrue on the
  bill and reverse on the return; e-invoice fires on save when applicable with a retry queue;
  POS and wholesale share the sales table with a bill type. **Adopt** the bucket choice, the
  auto-fire with retry, the one table (§9).
- **Both:** a posted invoice cannot be edited once an IRN exists (cancel within 24 h, else credit
  note); a bill with a return against it cannot be edited; period lock stops back-dated edits.
  **Adopt** (rules 1, 2, 5 of the brief).
- **Neither** posts stock from an order; Tally's order reserves nothing, GoFrugal shows "allocated
  to orders". Ours has `stock_reservation` designed — Q-19.

## 9. The two decisions the brief asked for

### 9a. COGS — perpetual, with a company switch

**Decision: perpetual (a COGS entry per outward), behind `accounts.cogs_mode` = `PERPETUAL`
(default) | `PERIODIC`.** Reasons:

1. The stock engine already values every outward row (`sml_cost_value`) at post time per the
   item's valuation policy. The figure is free; posting it costs two legs.
2. Every target trade in the brief (chain, supermarket, wholesale, electrical, toy) wants gross
   margin by day / branch / bill without waiting for a stock count. Periodic cannot give that.
3. Perpetual keeps the Inventory ledger equal to the stock valuation at every instant, which is
   the reconciliation an auditor asks for in a chain.
4. The Tally-shaped client exists; `PERIODIC` posts no COGS/INVENTORY legs and P&L uses closing
   stock — that is a report, not a posting change, so both modes share one engine.

**Where COGS is recognised: at the stock movement.** A DC posts DR `COGS` / CR `INVENTORY`; the
bill against it posts revenue only; a direct bill posts both; a return posts DR `INVENTORY` /
CR `COGS` (at the cost the ledger row carries) plus the revenue reversal. The purist alternative
(DR `GOODS_DELIVERED_NOT_BILLED` at DC, moved to COGS at the bill) is offered as Q-17b; it is more
correct on a month boundary and costs a role and two more legs per DC.

Consequence to record now: under `PERPETUAL` the future **purchase** posts DR `INVENTORY` (not
`PURCHASE`) / CR supplier, and `PURCHASE` / `PURCHASE_RETURN` roles become the periodic-mode
ledgers. The purchase design is not started, so this costs nothing yet.

### 9b. POS and wholesale — one `sale_bill`, `sb_bill_mode`

**Decision: one table, one module, one posting engine; `sb_bill_mode` = `POS` | `WHOLESALE`.**
The two differ in flow, not in fact: tender-first vs credit terms, walk-in vs named party, B2C vs
B2B (e-invoice), counter series vs branch series. Every downstream — return, DC link, register,
GSTR-1, receipts, loyalty, promotion, reports — would be doubled by a second table and would
still have to be joined back. `sale_bill` already carries `sb_counter_id`, `sb_session_id`,
`sb_device_*`, `sb_bill_type` (CASH/CREDIT), `sb_doc_type` (TAX_INVOICE / BILL_OF_SUPPLY),
`sb_category_id`. What the mode changes is defaults and gates, listed in the plan.

## 11b. Order / DC charges across part deliveries (user's ask, 2026-09-20) — **Q37**

Today the order's `txn_charge_detail` rows (`cdDocType = 'ORDER'`) never reach the bill; a part-billed
order loses its fixed freight or gets it typed in full on every bill. Neither Tally nor GoFrugal
tracks this. Rule proposed (default for Q37):

- **Rate-driven charges** (QTY / NET_QTY / KG / QTL / TON / PERCENT): the bill carries the order's
  *rate*; the amount is re-derived from the bill's own lines — proportional by construction.
- **FIXED lump charges**: every imported bill charge row records its source — **`cd_src_cd_id` +
  `cd_src_acc_year` on `public.txn_charge_detail`** (ALTER, Prathap). Remaining on the order
  charge = `cd_amount − Σ bill rows pointing at it on non-cancelled bills` — derived, never stored.
  On import each fixed charge is proposed **pro-rata by value share** of the imported lines, paise
  residue to the last bill, and **the last delivery takes the remainder**. The bill screen shows a
  "Charges from order" strip: order amount · already billed · this bill (editable) · remaining.
  Over-billing the remainder is refused server-side. Cancel/amend of a bill returns its share by
  derivation; `cancel-lines` drops the un-billed remainder with a notice.
- **DC → bill** applies the same rule with the DC's charge rows as source (the DC took them from the
  order the same way), so a charge crosses the chain exactly once.
