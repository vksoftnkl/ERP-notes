Decided 2026-10-22 (user: "margin is without tax profit amount in %", "let user know how much profit they earn", "keep silent the profit type"; chose **% on cost** over % of sale).

- **Profit % = (price wot − cost wot) ÷ cost wot × 100.** Stored in `ipm_price_a..d_markup_perc`; header "<level> Profit %". Before, it was worked on WITH-tax figures (By Rs overstated profit by the GST: ₹59 vs real ₹50) and By User blanked it.
- **Profit Type hidden**, every row saved "By User" — same value the Change Selling Price bulk gateway stores. The server never re-prices from it (only stores/returns), so hiding it is safe.
- Type % → price wot = cost wot × (1+%), + tax, rounded, then % re-worked from the ROUNDED price. Type price / price wot → % follows. Round Off change re-rounds that row's prices.
- **Cost / tax / unit-factor changes keep the prices**, only the % moves (`recalcRow(row, ProfitType)` now = `refreshProfit(row, true)`). Re-pricing is menu 30's job.
- Load: % from STORED wot figures (`refreshProfit(row,false)`), prices untouched — opening must never re-price (09-25 audit). Stored price with wot 0 → % blank.
- Line under the grid (`lblProfitSummary`, updateProfitSummary) — user: "keep texts very simple": `Profit per BOX (no tax):  WS ₹10.00 (10.0%) ↑ · RET -₹2.00 (-1.8%) ↓` (% = on cost). Amount+% green / red(-₹ loss), ↑/↓ = profit moved since the item was opened; tooltip has price, %, "was ₹x".
- ↑ green / ↓ red (user 10-22: plain arrows, not triangles; ONE place: priceUpArrow()/priceDownArrow() in item_price_delegate.h; bold full-size; HighlightedText colour on the selected cell) in the Price and Profit % CELLS vs the value at load (ItemPriceDelegate::paintChangeArrow, SavedValueProvider ← controller m_saved keyed by ipm_id; new rows no arrow). Colours = theme rate.above / rate.below (sale bill's rate-variance colours).
