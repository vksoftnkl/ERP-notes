Frontend deploys to https://vknexttimber-front.cloudjiffy.net/ from GitHub (vksoftnkl/ERP-frontend). CloudJiffy = Jelastic; TLS terminates at the platform NGINX balancer.

- The Jelastic Node.js layer whitelists **only application port 3000** (INPUT chain rejects the rest, no 80→app NAT). Any other bind = healthy app, balancer 502. Both repos' start configs pin 3000.
- App must serve **plain HTTP** (HTTPS upstream also 502s). Client `npm start` = `node scripts/ensure-build.js && next start -H 0.0.0.0 -p ${PORT:-3000}`.
- **Stale-build trap (found 2026-08-19)**: the deploy pulls into the existing app dir, so gitignored `.next/` survives; the old `[ -f .next/BUILD_ID ] || next build` guard then skipped the rebuild and served the previous bundle — new code on disk, old UI in the browser. `scripts/ensure-build.js` replaces it: rebuild when any source file is newer than `.next/BUILD_ID`, or when the `NEXT_PUBLIC_*` fingerprint changed (those are baked in at build time). Diagnose from outside with `curl -I <site>/_next/static/chunks/<any>.js` — `last-modified` is the build time.
- **The node installs production-only deps**, so anything `next build` needs must live in `dependencies`, not `devDependencies` (moved 2026-08-19: typescript, @types/*, tailwindcss, @tailwindcss/postcss, postcss, sass — the 55f2bc4 commit claimed to do this but only bumped versions). Second trap: `next build` typechecks every file in the tsconfig, so `vitest.config.ts` + `*.test.ts` dragged `vitest/config` into the prod build and failed it — `tsconfig.build.json` (wired via `next.config.mjs` → `typescript.tsconfigPath`) excludes them. Symptom of either: `jem service restart` → "Job for nodejs.service failed". Reproduce locally: copy `git ls-files` into a temp dir, `npm ci --omit=dev`, `npm start`.
- Client `.env` was untracked 2026-08-18 (it baked `NEXT_PUBLIC_API_BASE=https://127.0.0.1:3011` into prod bundles). Production API base must be set as a CloudJiffy env var **before build**.
- **Backend public URL = https://vknext-timber.cloudjiffy.net/api/v1** (confirmed 2026-08-20: dedicated IP 45.252.190.120, `POST /auth/login` → 400 = real endpoint). `erp-api.cloudjiffy.net` is NOT an env — it, and vknexttimber(-back|-api|-server), hit the wildcard openresty on 103.217.220.x and return "502 No such environment". A real env resolves to a dedicated IP with `server: nginx` + UPSTREAMID cookie — use that to distinguish. The frontend env is 103.205.141.171.
- Server CORS: production reads only `CORS_ORIGINS` in `ecosystem.config.js` (dev localhost defaults NOT merged); vknexttimber-front.cloudjiffy.net added 2026-08-18 alongside the Vercel aliases. Needs a backend redeploy/PM2 restart to take effect.
- **PM2 is the process manager, and it bypassed `npm start` (found 2026-08-20)**: the node's untracked `ecosystem.config.cjs` ran `script: node_modules/next/dist/bin/next, args: start` directly, so `scripts/ensure-build.js` NEVER ran in production — pulled commits stayed invisible, and once `.next` lost its `BUILD_ID` the app exited 1 in ~5ms (`ExecStart=/usr/local/sbin/nodejs start`, status=1/FAILURE, balancer 502). Fix: `ecosystem.config.cjs` is now tracked in the repo and runs `script: "npm", args: "start", interpreter: "none"`.
- **`PROCESS_MANAGER_FILE=ecosystem.config.cjs` must be set as a node env var.** `/usr/local/sbin/nodejs` otherwise does `APP_FILE=$(ls -1 $ROOT_DIR | grep "server.js\|app.js\|index.js" | head -1)` — a Next app has none, so the unit fails before PM2 even spawns. Node env also carries `PROCESS_MANAGER=pm2`, `UPDATE_PACKAGES_ON_RESTART=TRUE`, `NODE_OPTIONS=--max-old-space-size=2560`.
- `max_memory_restart` must exceed ~1.5G: `next build` peaks ~1.02 GB inside the PM2 tree, so the old `1G` would loop-kill it. Node disk is 19G (16% used) — OOM/disk are NOT the usual cause here.
- A platform restart can `pm2 delete` the app before dumping, leaving `~/.pm2/dump.pm2` unable to restore it. After any manual `pm2 start ecosystem.config.cjs`, always `pm2 save`.
- A `.env.production` on the node does **not** override a `NEXT_PUBLIC_*` already in the platform env — Next leaves existing `process.env` alone, so the dashboard var wins (the node's `.env.production` pointed at the dead erp-api host while the dashboard var was correct).
- Healthy `.next` is ~31 MB with a `BUILD_ID`; a few hundred KB means no build. App dir is `/home/jelastic/ROOT`, tracking branch `dev`.
- **CI/CD (added 2026-08-20)**: push to `dev` -> `.github/workflows/ci.yml` `build` job -> `deploy` job SSHes to the node (secrets `CLOUDJIFFY_SSH_KEY`, `CLOUDJIFFY_SSH_TARGET`; port var default 3022) and pipes `scripts/deploy-on-node.sh` over stdin. Non-interactive SSH has no nvm on PATH and no /.jelenv exports -- the script sources `$NVM_DIR/nvm.sh` and recovers `NEXT_PUBLIC_API_BASE` from /.jelenv or .env.production, refusing to build if neither has it.
- **Never `next build` into the live `.next`** -- it rewrites the directory the running server reads from: 16.9s of 502s measured. Build with `NEXT_DIST_DIR=.next-build` (wired through `next.config.mjs` `distDir` and `ensure-build.js`), then rename into place: 0.3s. Previous build kept at `.next.previous` for rollback.
- Deploy must call `node scripts/ensure-build.js --strict`, not `next build`: only ensure-build writes `.next/deploy-fingerprint`, and without it the app's own startup gate sees an env-fingerprint mismatch and rebuilds a SECOND time inside PM2. `--strict` (added 2026-08-20) disables the serve-the-previous-bundle fallback so CI fails loud.
- A deploy script that lives in the repo and runs `git reset --hard` rewrites itself mid-execution (bash reads scripts incrementally) -- it re-execs from a self-deleting temp copy. Piping it over `bash -s` sidesteps this, which is why CI does that.
- Deploys are pulled from Git by CloudJiffy; pushing does not redeploy — the user triggers it in the dashboard. Related: [[erp-local-https-setup]].
