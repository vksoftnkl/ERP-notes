The user's words, 2026-09-15: *"customer, party are both same when i create
customer under sales, supplier under purchase both unique ids are generated
from acc_ledger_master only, no need of list url becasue we hold the list in
grids, /get with company,branch,accYear,voucherId (/get,/approve,/reject,
/post,/cancel)"*.

**1. There is ONE party id.** `sales.customers.cus_id` **IS**
`accounts.acc_ledger_master.led_id`, and `purchase.suppliers.sup_id` likewise —
the id is generated by the ledger master when the customer/supplier is created.
Verified on the live DB (ids match one-for-one, names agree; the non-matching
rows are pre-convention test data). **There is no `cus_ledger_id` and no
`sup_ledger_id`, and neither should be added** — the receipt plan §2.11 and the
payment plan §2.3 had asked for them and both are now WITHDRAWN (notes 11).
So no endpoint resolves anything: never `customer_id OR party_id`, always one
`partyId`. The only thing worth adding is the FK *declaring* the identity
(`cus_id → led_id`), because nothing enforces it today.

**2. No `/list` route on any document.** Lists come from a **registered grid**
(`configured-grid-sql` / `grid-details`) driven by `NexApiTableView` — that is
how every list in the product already works. A new document needs a grid
registration, not an endpoint. Withdrawn: `/receipts/list`, `/payments/list`,
`/vouchers` list.

**3. One key shape for every route acting on an existing voucher** — `/get`,
`/approve`, `/reject`, `/post`, `/cancel` all take
**`companyId · branchId · accYear · voucherId`**. Not a bare id, not id+year,
not a `/:id/` path param. The tables are partitioned by `acc_year` and scoped
by company and branch, so those four ARE the key — the same `TxnDocKey` the
client already carries ([[txn-main-view-architecture]]).

**4. No approval step on any voucher** (user, 2026-09-15: *"remove approve
option because we have posted its a double work / if i want to POST from draft
is possible"*). The lifecycle is **DRAFT → POSTED → CANCELLED**: `/create`
saves the draft (no legs, no allocations, no number), `/post` runs straight off
it. A DRAFT already affects nothing, so it IS the unapproved state. Withdrawn
everywhere: `/approve` and `/reject` on receipts, payments and vouchers;
`um_can_approve` / `AppSession::canApprove`; the three `*_needs_approval`
settings. `APPROVED` stays legal in `ck_avh_status` and nothing writes it, so
the voucher-action routes are now three: `/get`, `/post`, `/cancel`.
**Not affected:** the write-off approver (`abj_approved_by`,
`accounts.writeoff_approval_above`) — a name recorded on a line, not a
workflow — and Collection Approval (menu 188), a separate screen.

**How to apply:** check any new endpoint spec against all three before writing
it. Applied already across `share/receipt/`, `share/payment/`,
`share/accounts/` and notes (11). See [[receipt-design]], [[payment-design]],
[[voucher-register-design]].
