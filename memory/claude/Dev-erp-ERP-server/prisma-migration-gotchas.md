This repo hand-authors migration folder timestamps as round future numbers (e.g. `20260615120000`, `20260615123000`) that run AHEAD of the real system clock. Consequences seen repeatedly when running `npm run prisma:migrate:dev`:

- **Out-of-order new migrations.** `migrate dev` stamps a new migration with the real clock — and it stamps in **UTC**, so even when the local wall clock (IST = UTC+5:30) is already past a hand-authored future timestamp like `20260616120000`, the UTC stamp (e.g. `20260616110805` at 16:38 IST) can still sort BEFORE it. If the new migration ALTERs an object that a later-sorting migration CREATEs, the shadow rebuild / fresh replay fails (P3006 "underlying table ... does not exist"). Fix: rename the new folder to a timestamp after the latest existing one and re-apply with `npm run prisma:migrate:deploy`.
  - **If the out-of-order migration was ALREADY applied** (DB up to date but `_prisma_migrations` has the bad-sorted name), renaming the folder alone makes Prisma see "applied migration missing locally" + "new pending migration". You must ALSO `UPDATE _prisma_migrations SET migration_name='<new>' WHERE migration_name='<old>'`. The `.sql` is unchanged so the checksum stays valid → `migrate status` reports clean.
  - **Verify a fresh replay actually works** (status "up to date" only checks the existing DB, NOT lexical-order replay): create a throwaway shadow db and run `npx prisma migrate diff --from-migrations prisma/migrations --to-schema-datamodel prisma/schema.prisma --shadow-database-url <url> --exit-code` → "No difference detected" means all migrations replay in order and match the schema.

  - **The fresh replay is BROKEN on DEV-v1 as of 2026-10-02**: `20260930190000_app_theme_tokens` inserts an "App Themes" menu under `menu_parent = 60` without an EXISTS guard, and menu 60 is only seeded later, so the shadow replay dies there with P3006 `menu_master_menu_parent_fkey`. Until it is fixed, verify a new migration by running its SQL on the live DB as `BEGIN; <migration.sql>; <checks>; ROLLBACK;` via `psql -v ON_ERROR_STOP=1`, then `migrate deploy`.

- **Checksum drift on already-applied migrations.** Migration `.sql` files get edited (often just whitespace/trailing newline) after being applied, so `migrate dev` wants to reset. There is a sanctioned script: `npm run prisma:migrate:sync-checksums` (scripts/sync-prisma-migration-checksums.js). Reconciling the checksum does NOT hide real schema drift — Prisma's shadow-vs-DB comparison still runs. Verify with `npx prisma migrate diff --from-schema-datasource prisma/schema.prisma --to-schema-datamodel prisma/schema.prisma --exit-code` ("No difference detected" == clean).
  - **First check whether the edit was intentional at all.** Seen 2026-07-13: an editor format-on-save stripped every blank line + the trailing newline from an applied migration (and from the open `prisma/*.prisma` fragment), with zero SQL change. `git diff` on the migration folder shows this instantly. When the edit is accidental, `git checkout -- prisma/migrations/<name>/migration.sql` is the right fix — it restores the original checksum with no reset. Syncing checksums instead would permanently bake the unintended reformat into the migration.

- **Master grids are seeded OUTSIDE migrations.** `grid_details`/`grid_columns` master rows (e.g. grids 9 godown, 11 item category) are created by 20260228113000 in the `grid` schema, then 20260318132503 DROPS that table when moving it to `fixed`. So on a freshly replayed/shadow DB those rows do NOT exist. Any seed migration inserting `grid_columns` for a hardcoded grid_id must guard on `EXISTS (SELECT 1 FROM fixed.grid_details WHERE grid_id = N)` or it violates `grid_columns_grid_id_fkey` on the shadow DB.

- **Still broken 2026-10-26, and `prisma db push` into an empty DB fails too** (schema-engine panic). To prove a
  seed agrees with a migration on ONE table (notes 158 menu restructure): `CREATE DATABASE erp_x; CREATE SCHEMA fixed;`
  `pg_dump --schema-only -t fixed.menu_master <live> | psql erp_x` (its sync trigger fails — harmless), `psql erp_x -f
  prisma/seed/Menu_Master.sql`, then diff the touched rows against live. The menu seed lacks 249/250/266/269/270
  (created only by migrations that skip on a fresh DB); notes 158 added them but was withdrawn, see [[notes-158-menu-restructure-withdrawn]].
- **Migrations run BEFORE seeds, so a migration cannot read seeded data.** `db:deploy` = `prisma migrate deploy && seed:run`, and the seed runner also fires at boot (DB_AUTO_SEED). So on a fresh database — and on the shadow DB `migrate dev`/`migrate diff --from-migrations` replays into — anything seeded from `prisma/seed` (the chart of accounts in `Account_Groups.sql`, state codes, menus, grids) is ABSENT while migrations run. A migration that inserts rows depending on them must either guard and no-op, or ship the logic as a function the seed calls (pattern used by `20260915110000_seed_acc_ledger_map` + `prisma/seed/Acc_Ledger_Map.sql`, which keeps one copy of the data). A failed SQL seed is logged and recorded in `public._erp_seed_history`; boot continues.
  - **A migration that UPDATEs seeded rows (menus, grids) must also edit the seed file**, or a fresh database replays the OLD values (the migration no-ops on an empty table, then the seed inserts the old row). Prove agreement, not just syntax (2026-09-28, notes 59 / 20260928200000 + Menu_Master.sql): `psql "$DATABASE_URL" -c 'CREATE DATABASE erp_x'` → `DATABASE_URL=<erp_x url> npx prisma migrate deploy --schema prisma/schema.prisma` → `DATABASE_URL=<erp_x url> npx tsx src/database/seed/seed.cli.ts --only=<Seed.sql>` → diff the rows against live → drop erp_x. ~1 min on PG18; a shell DATABASE_URL wins over .env for both prisma and the seed CLI (env.preload is plain dotenv, no override).

- **Partial indexes are invisible to Prisma — never declare them in the model.** The sale_quotation tables (migration 20260708120000) use partial unique/regular indexes (`WHERE sq_is_deleted = false` etc.). Prisma introspection ignores indexes with WHERE predicates, so if the model declares a matching `@@unique`/`@@index`, every `migrate dev` sees phantom drift and generates `CREATE [UNIQUE] INDEX` without the predicate, which fails 42P07 on the existing name (happened 2026-07-08: failed migration `20260708062230`, resolved with `migrate resolve --rolled-back` + deleting the generated folder). Fix: keep partial indexes DB-only (documented in fragment comments), declare only non-partial indexes in the model. Uniqueness for those paths must be checked app-side (or rely on the DB error).

- **@@map rename = destructive drop+create.** Adding `@@map("snake_case")` to an existing model makes `migrate dev` autogenerate DROP+CREATE (data loss) and the non-interactive shell can't confirm it. Author the migration by hand as `ALTER TABLE ... RENAME TO ...` (plus rename the `_pkey` constraint and the `_seq` sequence to the new conventional names) and apply with `migrate deploy`.

- **Physical column order drifts from the Prisma field order over time** (columns dropped/re-added by later migrations land at the end, e.g. `sqi_qty_case`/`sqi_qty_bill`/`sqi_qty_net_qty`/`sqi_qty_weight` in `sale_quotation_item` — fixed 2026-07-22). The user cares about DB column order matching the `.prisma` fragment's field order for readability in DB tools. Postgres has **no in-place column reorder** — fix by rebuilding the table: `CREATE TABLE x_new (<cols in target order>, <check constraints>)` → `INSERT INTO x_new (<cols>) SELECT <cols> FROM x` → `DROP TABLE x` → `ALTER TABLE x_new RENAME TO x` → recreate PK/indexes/FKs. Generate the column list/DDL from `pg_dump --schema-only -t <schema>.<table>` reordered by a small script rather than hand-typing — one missed/mistyped column among ~90 is easy to miss. Confirm first there's no incoming FK from another table (`\d` shows no "Referenced by" section) and check row count — empty/low-risk tables are safe to rebuild directly.
  - If the table-reorder is folded into an **already-applied, not-yet-committed** migration (rewriting its `migration.sql` in place rather than adding a new migration folder — matches this repo's habit of hand-editing local unshipped migrations): the migration file must be written to transform from the state *before* that migration ran (e.g. if it's the migration that added a column, the new column is absent from the INSERT/SELECT list so it takes its DEFAULT) — but the **local DB is already past that point**, so apply the equivalent rebuild directly against the live DB with a separately-adjusted column list (the new column included, selected from itself) inside its own transaction, matching what the rewritten migration file would produce.
  - `npm run prisma:migrate:sync-checksums` **defaults to a hardcoded pair of grid_sql migrations** — pass `--migration <name>` explicitly for any other migration or it silently reports `Updated: 0` for the one you actually changed.
  - Full verification chain: `prisma migrate status` (DB up to date) → `prisma migrate diff --from-schema-datasource ... --to-schema-datamodel ... --exit-code` (no logical drift) → throwaway shadow DB + `prisma migrate diff --from-migrations ... --to-schema-datamodel ... --shadow-database-url ... --exit-code` (fresh replay of ALL migrations in order still matches) — column order isn't part of Prisma's diff at all, only the shadow replay proves the rewritten migration file is self-consistent.

- **Postgres GENERATED ALWAYS columns need `@default(dbgenerated())` in the model.** Prisma has no generated-column concept: it reads the generation expression as a column default it doesn't own, and every `migrate dev` emits `ALTER TABLE ... ALTER COLUMN ... DROP DEFAULT`, which Postgres rejects with 42601 "is a generated column" — poisoning an otherwise unrelated migration. Hit 2026-08-08: adding `sqi_item_size` to sale_quotation_item failed on `abl_pending_amount`. The three generated columns (from 20260806090000) are `accounts.acc_bills.abl_pending_amount`, `accounts.acc_vouchers.av_signed_amount`, `.av_is_reconciled`. Fix is schema-only, no DDL: add the **no-argument** `@default(dbgenerated())` (valid in Prisma 6.19 — the arg-taking form would try to own the expression) to the field in the `prisma/accounts/*.prisma` fragment. Confirm the phantom DROP DEFAULTs are gone with `prisma migrate diff --from-url "$DATABASE_URL" --to-schema-datamodel prisma/schema.prisma --script` before retrying. Same class of problem as partial indexes above: DB objects Prisma can't express become perpetual phantom drift.

- **Hand-authored constraint names need `map:` in the model, or they read as drift.** A migration that writes `CONSTRAINT pk_<table> PRIMARY KEY (...)` (the house DDL style) makes every `migrate diff` report `[*] Renamed the primary key on columns (...)`, because Prisma assumes its own default `<table>_pkey`. Fix is schema-only: `@id(map: "pk_<table>")` on the field. Same applies to `@@unique(..., map: "uq_...")` and `@relation(..., map: "fk_...")` — all three were needed for the promotion_scheme tables (2026-08-21). A UNIQUE **constraint** and a `CREATE UNIQUE INDEX` of the same name are indistinguishable to Prisma, so either form is fine as an FK target.
  - **Verify a hand-authored migration BEFORE applying it** with the shadow replay: `psql -c 'CREATE DATABASE erp_shadow_x'` then `npx prisma migrate diff --from-migrations prisma/migrations --to-schema-datamodel prisma/schema.prisma --shadow-database-url <url> --exit-code`. "No difference detected" proves both that all migrations replay in order and that the result matches the datamodel — and it leaves no failed row in the real `_prisma_migrations` if the SQL is wrong. Note `prisma migrate diff --from-schema-datasource` against the live DB always reports `[-] Removed tables: _erp_seed_history` — that is the seed runner's own bookkeeping table, pre-existing and expected, not drift.

- **Apply ONE migration while a sibling's is pending** (seen 2026-10-09: an unapplied party-outstanding migration sorted before mine): `migrate deploy` would apply theirs too. Run `psql -v ON_ERROR_STOP=1 -1 -f <migration.sql>` then `npx prisma migrate resolve --applied <name>` (records the file's checksum). After editing that still-unshipped file, re-run the (idempotent) file and `npm run prisma:migrate:sync-checksums -- --migration <name>`.

Prisma wraps each migration in a transaction, so a P3018 failure rolls back cleanly — only the failed `_prisma_migrations` row remains; DELETE it (don't just `migrate resolve --rolled-back`) before retrying.

- **A leftover rolled-back row fakes checksum drift.** `resolve --rolled-back` keeps the row (with the *old* .sql checksum); re-applying the fixed migration adds a SECOND row under the same `migration_name`. `migrate status` still says "up to date", but a later `migrate dev` matches by name, hits the stale rolled-back row first, and demands a full reset ("was modified after it was applied"). Seen 2026-07-31 on `20260731080000_add_tender_types_and_master`. Diagnose by comparing `sha256sum <migration.sql>` to each row's `checksum` — if the *applied* row matches the file, nothing was edited; `DELETE FROM _prisma_migrations WHERE migration_name='<name>' AND rolled_back_at IS NOT NULL` and re-run. No reset, no data loss, and no need for `sync-checksums`.

- **An applied migration that grew new sections never runs them.** This repo hand-edits unshipped migrations in place, and with several sessions on the repo at once (see [[concurrent-claude-sessions]]) a file can be extended AFTER it was applied — the added SQL then exists only in the file. Prisma 6 here does NOT warn: `migrate status` said "Database schema is up to date!" while `20260915120000_receipt_voucher_prerequisites` (applied 16:43, file edited 16:59, 2026-09-15) was missing two whole sections on the local DB. Do not trust `_prisma_migrations`: compare `sha256sum prisma/migrations/<name>/migration.sql` to the row's `checksum`, and when they differ check the OBJECTS the added text creates (`pg_proc`, `pg_constraint`, `pg_trigger`, the inserted rows). An applied migration cannot be re-run, so the delta has to ship as a NEW idempotent migration — never as a hand-run psql script, which leaves fresh databases and the shadow replay disagreeing with this one.
