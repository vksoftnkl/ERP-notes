Local dev HTTPS (added 2026-08-15) serves TLS from `certs/localhost.{crt,key}` (gitignored), regenerated by `npm run cert:local`. Certs are signed by an mkcert CA at `~/.local/share/mkcert` that the user originally created 2026-02-25.

`sudo` on this machine requires a password, so mkcert and certutil were installed **without root**: `apt-get download mkcert libnss3-tools` + `dpkg-deb -x` + copy the binaries to `~/.local/bin` (already on the login PATH). The CA was registered with `TRUST_STORES=nss mkcert -install`, which skips the sudo-only system store.

**Why:** the same no-sudo trick works for any apt package whose binaries are relocatable, and `TRUST_STORES=nss` is what makes `mkcert -install` succeed unprivileged.

**How to apply:** browsers (Chromium + both Firefox profiles) and `curl` trust these certs already. **Node does not** — it ignores the system store, so any Node client hitting local HTTPS (tests, `scripts/perf/load-test.js`) needs `NODE_EXTRA_CA_CERTS=$(mkcert -CAROOT)/rootCA.pem` exported *before* the process starts; putting it in `.env` is too late, since dotenv runs after Node's TLS init. Production is unaffected — [[erp-https-prod-terminated-at-lb]].

**Stale-SAN gotcha (hit 2026-08-20):** DHCP reassigned the LAN IP (192.168.0.106 → 192.168.0.101) and the cert's SANs went stale. Firefox reports the resulting TLS rejection as *"Cross-Origin Request Blocked: The Same Origin Policy disallows reading the remote resource"* — it looks exactly like a CORS bug, but CORS was fine (`CORS_ORIGINS=*`, and the preflight already echoed `Access-Control-Allow-Origin`). Diagnose by comparing `hostname -I` against `openssl x509 -in certs/localhost.crt -noout -ext subjectAltName` before touching CORS config. Fix: `npm run cert:local -- --force` (the script auto-detects current LAN IPs), then restart the server — the cert is read once at bootstrap, and `nest start --watch` ignores a bare `touch`, so it needs a real content change or a manual restart.
