`components/ui/modal-portal.tsx` (`ModalPortal`, added commit bc8859d) fixes a real Chromium bug: pages are full-height flex shells whose grid lives in an `overflow: auto` scroll container with `position: sticky` headers, which Chromium promotes to its own compositing layer. A `position: fixed` modal overlay that's a DOM sibling of that scroller (not portaled) is not promoted, so the compositor can paint the scroller's layer on top — grid rows/headers bleed through the open modal as translucent ghost blocks, worst on repaint (hover, re-render) while the modal is up.

When ModalPortal was introduced it was wired into only `features/masters/reports/audit-logs/page.tsx`'s detail modal — **not** into the shared `ERPDynamicModalForm` (`components/design-system/ui/dynamic-modal-form.tsx`, used by every master page's add/edit modal, e.g. Item Master) or `components/ui/delete-confirm-modal.tsx`. Result: every master-page modal still glitched; only the audit-log/record-history popups (already portaled) were clean — exactly the symptom the user reported 2026-07-21 ("glitch in all modal popups, wasn't there before the record-history/audit-log UI change").

**2026-07-24 follow-up:** portaling + pre-promoting only the `.panel` (`will-change: transform`) was still insufficient on GPU-accelerated non-headless Chromium — dark ghost grid tiles kept bleeding over the panel (user reported it on the Item Group edit modal). Fix: promote the *whole* `.overlay` (backdrop + panel) into one isolated top-level composited layer via `isolation: isolate; transform: translateZ(0);` on the `.overlay` rule of both `components/design-system/ui/dynamic-modal-form.module.scss` and `components/ui/delete-confirm-modal.module.scss`. Can't be reproduced/verified headlessly (headless doesn't GPU-composite — that's why it "works" there); verify on the real browser with a hard refresh. Any future modal overlay needs the same overlay-level promotion, not just panel-level.

**2026-08-05 app-wide sweep:** the user hit it again on the Account Ledger edit modal (dark tiles over the GST & Tax fields). That page renders its own overlay inline with `dynamicFormStyles.overlay` instead of going through `ERPDynamicModalForm`, so it never got the portal. Swept every overlay in the app: portaled `features/masters/accounts/account-ledger/page.tsx` (form modal + grid-settings dialog), `components/master/crud-master-page.tsx` (the grid-settings dialog shared by ~36 master pages), `features/masters/settings/price-level-configuration/page.tsx`, and the five stock modals (`opening-stock-list-modal`, `opening-stock-audit-notes-modal`, both `BulkLoadItemsModal`s, `PhysicalStockListModal`); added the `isolation: isolate; transform: translateZ(0)` promotion to the overlays that own their CSS (stock `.stockBrowserModalOverlay`/`.inlineMasterOverlay`, record-history, audit-logs, price-level, quotation `.modalOverlay`). Audit trap: plain `grep` skips `item-master-page.tsx` and `quotation-entry-view.tsx` (see [[erp-grep-skips-binary-files]]) **and** a `styles.overlay` pattern misses `dynamicModalStyles.overlay` — the CrudMasterPage one was found only with `grep -ran "Styles.overlay\|styles.overlay"`. Portaling is safe here because the global modal CSS keys off `.erp-ms-modal*` classes (not a `.erp-master-shell` ancestor) and the modal-internal page-module classes use literal colors; the one real consequence is `var(--primary)` inside a portaled overlay now resolving to the `:root` maroon `#7b1515` instead of the master skin's `#b91c1c`.

**2026-08-06 third failure mode — scrim over the panel:** even fully portaled + overlay-promoted, the Record History modal showed a *dark ghost rectangle over its own top-left content* on open and on the repaint a mouse click (left or right) triggers. Cause: the scrim was painted as `background:` on `.overlay` (same base layer) while the panel stayed un-promoted, so its freshly-created sub-layers (sticky `.listHead`, the `overflow:auto` grid scroller) composited a stale/partial frame with the scrim over the panel. Fix = replicate `dynamic-modal-form`'s full three-part structure: (1) overlay keeps `isolation: isolate; transform: translateZ(0)` and **no background**, (2) a dedicated `.backdrop` child (`position:absolute; inset:0; z-index:0`) owns the scrim + close-on-mousedown, (3) panel gets `position:relative; z-index:1; will-change: transform, opacity` so its GPU layer exists before first paint. Applied to record-history (JSX + CSS); CSS-only panel promotion also added to audit-logs `.modal`, quotation `.modalPanel` (shared by `components/modal-shell.tsx`), stock `.inlineMasterPanel` and `.stockBrowserModalPanel`. Headless can verify structure only (scrim pixel ≈ rgb(140,140,140) over white, backdrop click closes) — the ghost itself needs real GPU Chromium.

**2026-08-08 backdrop-split sweep complete:** the user hit the ghost/"shrinking" on the Quotation Visible Settings dialog — the three overlays still carrying the scrim as `background:` on the overlay itself got the full split: quotation `.modalOverlay`→ new `.modalBackdrop` + backdrop `<button>` in `components/modal-shell.tsx` (covers all 7 quotation dialogs), audit-logs `.overlay`→`.overlayBackdrop` + backdrop button in its detail popup, and record-history **standalone page**'s `RecordHistoryViewer` audit-detail overlay (Tailwind, was inline + un-portaled + `z-[210]`) — now `ModalPortal`-wrapped, `isolate transform-gpu` overlay, backdrop button with the scrim, panel `relative z-[1] will-change-transform`, z aligned to `z-[var(--erp-z-modal)]`. Outside-click close moved from overlay target-check `onMouseDown` to the backdrop button in all three. `.inlineMasterOverlay` in stock-page.module.scss still has scrim-on-overlay but has **no TSX consumer** (dead CSS); `(marketing)/erp-data-demo` overlays left as-is. Everything else already had the backdrop split. Verified headlessly (structure + backdrop-click close + screenshots) on quotation & audit-logs.

**Why:** ModalPortal is a per-adopter opt-in, not automatic — nothing forces new or existing modal components to use it.
**How to apply:** Fixed by wrapping both `ERPDynamicModalForm`'s overlay and `DeleteConfirmModal`'s overlay in `<ModalPortal>`. Any new modal/popup component with a `position: fixed` overlay rendered inline in a page (not already portaled) needs the same wrap. Before wrapping, check the modal's CSS module for custom properties inherited from a page-scoped ancestor (e.g. `.page { --token: ... }`) rather than `:root` — those collapse to nothing once portaled to `document.body` and need hoisting into a mixin applied to the overlay too, per the caveat already documented in `modal-portal.tsx`'s own comment. In this codebase `--erp-ms-accent`/`--erp-radius` etc. are `:root`-scoped in `styles/library/_master-shell.scss` and `app/globals.css`, so no token migration was needed for these two.
