The local ERP stack is **HTTPS end-to-end** (set up 2026-08-15). Both repos keep their own gitignored `certs/localhost.crt` + `.key`, generated by a `npm run cert:local` script (`scripts/generate-local-cert.js`) that prefers **mkcert** and falls back to openssl. mkcert lives at `~/.local/bin/mkcert` (often missed by non-login shells — the script searches that path explicitly) and its CA is already installed, so browsers and `curl --cacert "$(mkcert -CAROOT)/rootCA.pem"` trust the certs with no warning.

- **Client** (`ERP client`): `npm run dev` serves HTTPS via Next's `--experimental-https{,-key,-cert}` flags; `npm start`/`start:https` runs `https-server.cjs` (override paths with `HTTPS_CERT_PATH`/`HTTPS_KEY_PATH`). `dev:http`/`start:http` keep the plain-HTTP escape hatch. `.env` → `NEXT_PUBLIC_API_BASE=https://127.0.0.1:3011/api/v1`.
- **Server** (`ERP server`): `.env` has `HTTPS_ENABLED=true` + `HTTPS_CERT_PATH=certs/localhost.crt`.

**Why the client must not be served over plain HTTP:** `resolveApiBase()` in both `lib/api/client.ts` and `hooks/useApi.ts` **downgrades an https API base to http when `window.location.protocol === "http:"`**. The API is TLS-only, so an HTTP-served page silently rewrites the base and every request dies on connection reset. The two files duplicate this logic — change both.

**Gotcha — a running server holds the cert it loaded at startup.** Regenerating certs on disk changes nothing until the process restarts; the served cert can differ from the on-disk one. Diagnose by comparing them: `echo | openssl s_client -connect 127.0.0.1:3011 -servername localhost | openssl x509 -noout -subject -issuer` vs `openssl x509 -in certs/localhost.crt -noout -subject`. A `curl --cacert` returning **000** with `SSL certificate problem: self-signed certificate` (while `curl -k` returns a real status) is this exact symptom. Same family of stale-process trap as [[erp-stale-dist-404]].

**LAN caveat:** the client cert includes the detected LAN IPv4 (matching `allowedDevOrigins: ["192.168.0.*"]` in `next.config.mjs`), but the **server cert's SANs are only `localhost`/`127.0.0.1`/`::1`** — its generator hardcodes that host list. `resolveApiBase()` rewrites the API hostname to the page's hostname when browsing over LAN, so API calls to `https://<lan-ip>:3011` fail cert validation until the server cert is regenerated with that IP.
